# RG Ballet — хранение заявок и мини-CRM

## 1. Цель

Для сайта RG Ballet не требуется полноценная CRM.

Школа одна, заявок немного, выбор преподавателя и дальнейшая запись клиента выполняются владельцем вручную.

Необходимо реализовать простую систему:

- приём заявок с сайта;
- хранение заявок на сервере;
- удобный просмотр заявок владельцем через браузер;
- изменение статуса заявки;
- добавление внутренних заметок;
- уведомление владельца о новой заявке;
- возможность выгрузки данных в Excel/CSV;
- резервное копирование базы.

Основное хранилище данных — SQLite.

Не использовать Excel-файл, Яндекс Диск или Google Sheets как основную рабочую базу.

```text
Пользователь сайта
        ↓

        ↓
┌──────────────────────┐
│ Админ-панель /admin  │
└──────────────────────┘
        ↓
```

Дополнительно:

```text
Новая заявка
      ↓
уведомление владельцу
      ↓

```

В дальнейшем можно добавить Telegram-уведомления.

# 3. Frontend

Основной сайт разрабатывается на:

- Astro;
- HTML;
- CSS;
- Vanilla JavaScript.

Astro остаётся преимущественно статическим сайтом.

Серверная логика используется только там, где она действительно нужна:

- обработка заявок;
- работа с SQLite;
- авторизация администратора;
- админ-панель;
- экспорт данных;
- резервное копирование.

---

# 4. Форма заявки

Форма должна быть собственной, свёрстанной по макету Figma.

Не использовать внешний iframe Яндекс Форм.

Минимальные поля:

```text
Имя
Телефон
Email — при необходимости
Комментарий
Согласие на обработку персональных данных
```

Телефон является основным контактом.

Email можно сделать необязательным.

Не собирать лишние данные.

---

# 5. Отправка формы

Frontend отправляет данные методом POST:

```text
POST /api/lead.php
```

Рекомендуемый формат:

```json
{
  "name": "Анна",
  "phone": "+79991234567",
  "email": "",
  "comment": "Хочу записаться на пробное занятие"
}
```

Сервер должен:

1. принять данные;
2. проверить обязательные поля;
3. нормализовать данные;
4. защититься от очевидного спама;
5. записать заявку в SQLite;
6. присвоить статус `Входящая`;
7. записать дату и время создания;
8. отправить уведомление владельцу;
9. вернуть frontend результат.

Пример успешного ответа:

```json
{
  "success": true
}
```

Пример ошибки:

```json
{
  "success": false,
  "message": "Не удалось отправить заявку"
}
```

Не передавать пользователю технические детали внутренних ошибок.

---

# 6. SQLite

Основная база:

```text
/private/data/rgballet.db
```

База данных не должна находиться внутри публичной директории сайта.

Нельзя размещать SQLite-файл таким образом, чтобы его можно было скачать через URL.

Пример:

```text
/home/user/
├── private/
│   ├── data/
│   │   └── rgballet.db
│   └── backups/
│
└── public_html/
    ├── index.html
    ├── assets/
    ├── api/
    └── admin/
```

---

# 7. Таблица leads

Базовая структура:

```sql
CREATE TABLE leads (
    id INTEGER PRIMARY KEY AUTOINCREMENT,

    created_at TEXT NOT NULL,
    updated_at TEXT,

    name TEXT NOT NULL,
    phone TEXT NOT NULL,
    email TEXT,

    comment TEXT,

    status TEXT NOT NULL DEFAULT 'Входящая',

    admin_note TEXT
);
```

При необходимости структуру можно расширять.

---

# 8. Статусы заявок

На первом этапе использовать простой набор:

```text
Входящая
Связались
Записана
Клиент
Отказ
```

Назначение:

### Входящая

Новая заявка, с которой ещё никто не работал.

### Связались

Владелец или администратор связался с клиентом.

### Записана

Клиент записан на пробное или другое занятие.

### Клиент

Человек фактически стал клиентом школы.

### Отказ

Заявка закрыта без записи.

Не использовать один общий статус `Отработано`, потому что он не показывает результат обработки заявки.

# 9. Админ-панель

Адрес:

```text

```

Админ-панель должна быть простой и удобной для использования с телефона.

Главная задача администратора — работа с заявками.

Не создавать сложную CRM.

Пример:


Это основной интерфейс владельца школы.

# 12. Изменение статуса

Статус должен изменяться через `select`.

Например:

```text
[ Входящая ▼ ]

Входящая
Связались
Записана
Клиент
Отказ
```

Изменение желательно сохранять без перезагрузки страницы.

Например:

```text
POST /api/admin/update-lead.php
```

Передавать:

```json
{
  "id": 25,
  "status": "Записана",
  "admin_note": "Пробное занятие 15 сентября"
}
```

# 13. Авторизация

`/admin` должен быть закрыт от публичного доступа.

На первом этапе достаточно:

- логин;
- пароль;
- PHP session.

Пароль:

- не хранить в открытом виде;
- использовать `password_hash()`;
- проверять через `password_verify()`.

После успешной авторизации создавать серверную сессию.

Все admin API должны проверять авторизацию.

---

# 18. Резервные копии

SQLite удобно резервировать, потому что база хранится в одном файле.

Основной файл:

```text
/private/data/rgballet.db
```

Резервные копии:

```text
/private/backups/
```

Пример:

```text
/private/backups/
├── rgballet_2026-09-12.db
├── rgballet_2026-09-11.db
├── rgballet_2026-09-10.db
└── ...
```

Создавать автоматическую копию минимум один раз в сутки.

---

# 19. Политика хранения backup

Минимальный вариант:

```text
7 ежедневных копий
4 недельных копии
6 месячных копий
```

Так как база маленькая, объём хранения будет незначительным.

В дальнейшем одну из резервных копий можно дополнительно отправлять во внешнее российское облачное хранилище.

Но внешнее облако не должно быть основной рабочей базой.

---

# 20. Важный момент с SQLite backup

Не копировать активный SQLite-файл произвольным способом во время записи.

Использовать корректный механизм резервного копирования SQLite либо обеспечить блокировку на время создания копии.

Цель — не получить повреждённый backup.

---

# 21. Защита формы

Минимальная защита:

- серверная валидация;
- ограничение длины полей;
- проверка типа данных;
- prepared statements;
- защита от SQL injection;
- rate limit;
- honeypot-поле против простых ботов;
- CSRF-защита там, где она необходима;
- логирование ошибок на сервере.

Не доверять данным, пришедшим из браузера.

---

# 22. Prepared statements

Никогда не формировать SQL через конкатенацию пользовательских данных.

Неправильно:

```php
$sql = "INSERT INTO leads (name) VALUES ('$name')";
```

Использовать prepared statements.

Например PDO SQLite:

```php
$stmt = $pdo->prepare(
    'INSERT INTO leads (created_at, name, phone, email, comment, status)
     VALUES (:created_at, :name, :phone, :email, :comment, :status)'
);

$stmt->execute([
    ':created_at' => $createdAt,
    ':name' => $name,
    ':phone' => $phone,
    ':email' => $email,
    ':comment' => $comment,
    ':status' => 'Входящая'
]);
```

---

# 23. Персональные данные

Форма собирает персональные данные.

Основные данные:

- имя;
- телефон;
- email;
- комментарий клиента.

Не собирать больше информации, чем требуется для записи клиента.

Под формой должен находиться чекбокс согласия на обработку персональных данных.

Рядом должна быть ссылка на соответствующий документ сайта.

---

# 24. Логирование

Технические ошибки записывать отдельно.

Например:

```text
/private/logs/
```

Не выводить stack trace или внутреннюю информацию пользователю.

Логи не должны содержать лишние персональные данные.

Например:

```text

```

Там могут находиться:

- параметры администратора;
- данные SMTP;
- секреты;
- пути;

Не реализовывать:

- рабочую базу в Excel;

# 30. Основная концепция

Итоговая архитектура:

```text
                      ┌→ Email владельцу
                      │
Форма сайта → PHP → SQLite
                      │
                      ↓
                   /admin
                      │
              ┌───────┴────────┐
              ↓                ↓
         изменить статус    экспорт CSV/XLSX
```

Отдельно:

```text
SQLite
   ↓
ежедневный backup
   ↓
/private/backups/
```

# 31. Основной принцип разработки

Система должна быть максимально простой.

Приоритеты:

1. надёжность;
2. удобство владельца;
3. мобильная версия админки;
4. безопасность персональных данных;
5. простое резервное копирование;
6. возможность дальнейшего расширения.

Не усложнять архитектуру ради будущих функций, которые пока не нужны.

При этом код и структура базы должны позволять в дальнейшем без полной переделки добавить:

- управление контентом сайта;
- преподавателей;
- фотографии;
- новости;
- дополнительные статусы;
- Telegram-уведомления;
- расширенную CRM.
