# Правила работы

* Общайся только на русском.
* В обычных ответах пиши кратко.
* Код предоставляй полностью, когда изменяется целый файл.
* Не сокращай важные технические объяснения.
* Не пиши код, сперва алгоритм действий.
* Если есть упущение в действиях задай вопрос.
* Пиши действия которые мне нужно сделать поступательно.
* Перед изменением файла сначала составь план.
* Не меняй архитектуру проекта без необходимости.
* Не создавай новые зависимости без согласования.
* Используй существующий стиль кода.
* После завершения перечисли изменённые файлы.
* Не сканируй рекурсивно `node_modules/`, `dist/`, `.astro/` и `.initial_data/`.
* Открывай их только когда задача прямо связана с зависимостями, сборкой или исходными макетами.
* Не читай все документы проекта перед каждой задачей. Сначала определи, какие файлы и требования относятся к запросу, затем изучай только их.
* Используй документы по ситуации:

  * `package.json` и `README.md` — команды, зависимости, сборка и публикация.
  * `docs/TZ.md` — требования к страницам, секциям и пользовательским функциям; сверяй только относящиеся к задаче пункты.
  * `docs/ARCHITECTURE.md` — границы компонентов, структура проекта и интеграции.
  * `docs/DECISIONS.md` — только решения, относящиеся к изменяемой части проекта; найди нужный раздел поиском, не перечитывай документ целиком без необходимости.
  * `docs/QUESTIONS.md` — когда задача затрагивает открытый вопрос или требует принять решение.
* Для небольшой локальной правки обычно достаточно целевого файла и его непосредственных зависимостей. Не перечитывай документы, уже изученные в текущем чате, если их содержимое не изменилось и задача не требует повторной сверки.
* Маршрутизация повторяющихся задач:

  * Политика персональных данных и cookie — `CookieBanner.astro`, `BaseLayout.astro`, страницы политики и согласия; соответствующее решение в `DECISIONS.md`.
  * Будущее и планирование — сначала `QUESTIONS.md`; `ARCHITECTURE.md` подключай только для оценки технического влияния.
  * Яндекс Форма — `YandexFormModal.astro`, `index.astro`, при необходимости `FormModal.astro` и форма в `Footer.astro`; сверяй разделы о форме и персональных данных в решениях.
  * Адаптивность — только затронутый компонент и его стили; ищи относящееся к нему решение по заголовку секции в `DECISIONS.md`.
  * Ссылка на Яндекс Карты — `src/config/contacts.js` и использующий ссылку участок `Footer.astro`; при необходимости раздел «Контактные данные».
  * Создание или настройка Astro-проекта — `package.json`, `astro.config.mjs`, `README.md` и соответствующий раздел `ARCHITECTURE.md`.
  * Kinescope — `VideoModal.astro`, `About.astro` и раздел «Видео о студии» в решениях.
  * Мобильное меню — `Header.astro` и раздел «Мобильное меню» в решениях.
  * Форма заявки — форма в `Footer.astro`, `FormModal.astro` или `YandexFormModal.astro` по месту изменения; связанные скрипты и раздел «Форма заявки» в решениях.
  * Отзывы из Яндекса — массив отзывов и разметка в `Footer.astro`, раздел «Отзывы» в решениях; не перечитывай правила формы, если задача их не затрагивает.
* Если в требованиях есть противоречия, сначала укажи на них
* Новые нерешённые вопросы записывай в `docs/QUESTIONS.md`.
* Принятые технические решения записывай в `docs/DECISIONS.md`.

## Технологический стек

* Framework: Astro.
* Frontend: HTML, CSS, Vanilla JavaScript.
* CSS-фреймворки и UI-фреймворки не использовать.
* React по умолчанию не использовать; добавление возможно позже только после отдельного согласования.
* Package manager: npm.
* Рабочая версия Node.js: 24.16.0.
* Рабочая версия npm: 11.13.0.
* npm registry: `https://npm-mirror.gitverse.ru`.
* Источник дизайна: Figma.
* Основные макеты: desktop 1920 px и mobile 360 px.
* Изображения сайта хранить в `public/images`.
* Остальные статические файлы хранить в `public`.

## Хостинг и деплой

* Production должен размещаться на российском хостинге.
* Основные кандидаты: Timeweb и SpaceWeb; окончательный вариант пока не выбран.
* Домен: `rgballet.ru`, регистратор — REG.RU.
* Не считать Vercel целевой production-платформой.
* Публиковать содержимое производственной сборки `dist`.
* GitHub и GitHub Actions для автоматического деплоя пока являются планируемыми решениями.

## Формы и CRM

* Форма должна визуально соответствовать Figma.
* Не встраивать стороннюю форму, если она нарушает дизайн.
* Поля первой версии формы: имя и телефон.
* Данные клиентов должны обрабатываться и храниться в инфраструктуре, соответствующей требованиям РФ.
* Новая заявка должна отправлять уведомление на email; уведомление в мессенджер желательно.
* Не реализовывать админ-панель или CRM до выбора варианта: собственная админ-панель, собственная CRM или внешняя CRM.
* Архитектура должна допускать последующую интеграцию сервиса онлайн-записи.

## Инфраструктура

* SSL обязателен.
* Резервные копии обязательны.
* Яндекс Метрика запланирована.
